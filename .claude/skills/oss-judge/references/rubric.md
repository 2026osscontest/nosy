## G8. 실물 반증 게이트 — **가장 먼저, 가장 엄격하게 판정한다**

트렌드 기사·업계 담론·리서치 문서가 "빈틈"이라고 말하는 것은 **증거가 아니다.** 실물을 직접 찾아 반증을 시도하고, 반증에 실패했을 때만 통과시킨다.

### 판정 절차 (전부 수행. 하나라도 건너뛰면 판정 무효)

1. **웹 검색 최소 3회** — 한국어 1회 + 영어 2회. 도구 이름이 아니라 **문제 서술**로 검색한다.
   (`"<문제> open source tool"`, `"<대상 표준> validator/scanner/linter"`, `"<도메인> 자동화 오픈소스"`)
2. **GitHub 직접 검색** — `gh search repos` / `gh search code`. 유사 도구의 스타·최근 커밋·릴리스를 확인한다.
3. **공식 주체 로드맵 확인** — 그 표준·생태계를 관리하는 조직(재단·WG·벤더)의 **로드맵 문서와 이슈 트래커**를 직접 연다. "언젠가 만들 수도"가 아니라 **문서에 적혀 있는지**를 본다.
4. **호스트가 흡수했는지 확인** — 우리가 붙으려는 대상(에이전트·프레임워크·플랫폼)이 그 기능을 **이미 내장**했는지 공식 문서로 확인한다.

### HIT 조건 (하나라도 해당하면 기각)

| 조건 | 판정 |
|---|---|
| 같은 문제를 푸는 도구가 **3개 이상** 검색된다 | **HIT** — 개수 자체가 시장 포화의 증거다 |
| **공식 주체가 이미 만들고 있다** (저장소 존재, 로드맵 명시, SEP/RFC 채택) | **HIT** — 절대 이길 수 없다 |
| 우리가 붙으려는 **호스트가 그 기능을 내장**했다 | **HIT** — 어댑터의 존재 이유가 소멸한다 |
| 상용 제품이 이미 있고 우리 차별점이 "오픈소스라는 것"뿐이다 | **HIT** |

### 통과 조건

위 4개 검색을 모두 수행하고도 **유사 도구가 2개 이하**이며, **공식 주체 로드맵에 없고**, **호스트가 내장하지 않았을 때만** 통과. 판정문에 **검색어와 확인한 URL을 남긴다.**

### 1라운드 실패 기록 — 같은 실수를 반복하지 말 것

2026-08-16 첫 채점에서 리서치 문서의 "빈틈 10개"를 근거로 후보를 만들었고, 실물 검증을 하지 않아 **1·2·3·4위가 전부 오판**이었다.

| 후보 | 리서치의 주장 | 실제 | 교훈 |
|---|---|---|---|
| mcp-conform (1위 88.8) | "MCP 컨포먼스 스위트가 없다" | **`github.com/modelcontextprotocol/conformance` 공식 저장소 존재.** SEP-2484로 "Standards Track SEP는 컨포먼스 시나리오가 있어야 Final 도달" 규칙화. SEP-1730 SDK 티어 심사에 사용 중 | **표준 조직은 컨포먼스를 반드시 직접 만든다.** 표준 검증 도구는 구조적으로 공식 진영과 충돌한다 |

**공통 패턴 — 다음 라운드에서 특히 의심할 것**
- 표준·규격의 **검증기/린터/컨포먼스** → 공식 진영이 만든다. 거의 항상 HIT.
- 인기 도구의 **관측성 어댑터/브리지** → 호스트가 내장한다. 거의 항상 HIT.
- 신생 생태계의 **보안 스캐너** → 상용 보안 벤더가 즉시 진입한다. 거의 항상 HIT.
- "**전부 수작업이다**", "**아직 아무도 안 만들었다**"는 서술 → 검색 한 번이면 반증된다.

**게이트 판정 시 주의**
- G1: 최종 사용자가 개발자여도 "개발자용 SaaS 웹서비스"는 배포 아티팩트가 없으면 G5에서 다시 걸린다.
- G2: 레드오션 카테고리에 속해도 **문제를 한 층 위로 올리면** 통과할 수 있다. 단 **한 층 위로 올린 그 자리도 G8로 다시 검증해야 한다.** 1라운드의 4건이 정확히 이 지점에서 죽었다.
- G3: "오픈 웨이트 모델 fallback 경로를 함께 구현"하면 통과. 이 경로를 넣을 수 있는지 먼저 검토하라.

# PART 1. 1차 서면평가 — 30점

> 1차는 **결과보고서 + 소스코드 + 시연영상 3종만**으로 평가된다. 발표 기회가 없다. 심사위원은 코드를 실행하지 않는다.
> 자유과제 수상 17팀 기준 **1차 통과는 약 34팀**. 여기가 실질 관문이다.

## 1-1. 프로젝트 구조 및 코드 완성도 (6점)

*"코드의 가독성, 주석의 활용도, 구조의 합리성 / 코드가 목적에 맞게 제 기능을 하는 정도"*

아이디어 단계에서는 **"이 문제가 좋은 구조를 강제하는가"**를 본다.

| 점수 | 앵커 |
|---:|---|
| **6** | 문제 정의에서 모듈 경계가 자동으로 도출된다 (core / adapter / cli 처럼). 어댑터를 하나 더 붙이는 것이 곧 기능 확장이 되는 구조. Mocka의 멀티모듈(core/orm/odm) 수준 |
| **4** | 구조는 명확하나 범위가 넓어 D-11 안에 정리할 여유가 없다 |
| **2** | 구조가 문제에서 도출되지 않고 개발자가 임의로 나눠야 한다 |
| **0** | 단일 스크립트로 수렴하거나, 반대로 3개 이상의 배포 타깃(확장+서버+CLI)으로 흩어진다 |

## 1-2. 오픈소스 프로젝트로의 발전 가능성 (6점)

*"출품작이 오픈소스 프로젝트로 진행 중이거나 향후 발전할 수 있는 가능성"*

| 점수 | 앵커 |
|---:|---|
| **6** | 확장점이 설계에 내재한다(플러그인/어댑터/룰셋). 남이 자기 환경용 어댑터를 추가할 동기가 명확하고, 그 작업이 good first issue로 자연 분해된다. 대회가 끝나도 계속 커밋할 이유가 팀 외부에 존재한다 |
| **3** | 발전 여지는 말할 수 있으나 코드 구조에 확장점이 없어 로드맵이 선언에 그친다 |
| **0** | 일회성 데모. 우수작 43팀 다수가 제출 후 커밋이 끊겼다 — 이 형태로 보이면 이 6점 + 2차 커뮤니티 10점이 **동시에** 위험하다 |

## 1-3. 개발 문서의 구체성 (6점)

*"개발 문서가 구체적이며 쉽게 이해할 수 있으며 목적에 맞게 작성된 정도"*

**주의: 문서 분량은 변별력이 없다.** 실측상 README 크기 중앙값은 상위상 6.6KB < 중위상 13.6KB로 **역전**한다. 1027줄·976줄짜리 서술형 README는 오히려 감점이다.

| 점수 | 앵커 |
|---:|---|
| **6** | 문제가 **이미 존재하는 스펙**에 기반해 문서가 곧 검증 가능한 명세가 된다(MCP 2026-07-28, OTel GenAI semconv, SKILL.md, KWCAG 2.2, SLSA/in-toto 등). 아키텍처가 mermaid 다이어그램 1장으로 설명되고, README 상단 데모 GIF 한 장으로 "무엇을 하는 물건인지" 3초 안에 전달된다 |
| **4** | 문서화는 가능하나 개념 설명부터 시작해야 한다 (심사위원이 도메인을 모른다는 전제로 판단하라) |
| **2** | 설명에 3문단 이상이 필요하다 |
| **0** | 무엇을 하는 물건인지 팀 내부에서도 문장이 갈린다 |

## 1-4. 프로젝트 혁신성 (6점)

*"프로젝트의 기술력과 기술적 수준(최신 기술 활용 정도)"*

**2026년 기준으로 채점한다. 2025년에 참신했던 것은 지금 0점이다.**

| 점수 | 앵커 |
|---:|---|
| **6** | 최신 기술 시그널 TOP10 중 **2개 이상**을 정면 채택하고, **스펙 이름 + 버전**을 발표에서 말할 수 있다. (예: "MCP 2026-07-28 stateless 스펙 준수", "OTel GenAI semconv v1.42 기반, pre-stable이라 버전 핀 고정") |
| **4** | 시그널 1개를 정확히 채택 |
| **2** | 최신 기술을 쓰지만 표준명·버전을 특정할 수 없다. "AI를 활용했다"는 2026년에 **전제**이지 점수원이 아니다 |
| **0** | 안티 시그널 TOP10에 해당 (LangChain RAG 파이프라인 / 벡터DB 중앙 배치 / 프롬프트 엔지니어링을 핵심 기여로 제시 / 구세대 모델명 명시 등) |

## 1-5. 프로젝트 팀워크 (6점)

*"(팀) 역할 분배와 운영에서 보여지는 팀워크의 수준 ※ github Issues, review, pull requests, commit, merge, 커뮤니티 등 관리체계"*

2~3인 팀이므로 **팀 기준**으로 평가된다. 아이디어 단계에서는 **"3인이 병렬로 일할 수 있게 쪼개지는가"**를 본다.

> 실제 탈락 사례 인용: *"저장소를 보면 협업 능력이 많이 어설프다는 것이 티가 난다"* — 심사위원은 레포를 열어 이슈·PR·리뷰·브랜치 흔적으로 협업 수준을 즉시 읽는다.
