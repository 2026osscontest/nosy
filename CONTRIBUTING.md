# Contributing to Nosy

Thanks for looking. Nosy is a diagnostic tool, which shapes what kinds of contributions matter most
here — a check that fires when nothing is wrong does more damage than a missing check, so reports of
**false positives** are the most valuable thing you can send.

## Ways to contribute

| | |
|---|---|
| **Report a false positive** | Nosy flagged something that was actually fine. See [below](#reporting-a-false-positive) — this is the highest-value report. |
| **Report a bug** | Crash, wrong output, UI problem. |
| **Write an adapter** | Teach Nosy to diagnose a tool it doesn't know yet. See [the walkthrough](#writing-a-new-adapter). |
| **Improve docs** | Including translations of `README.ko.md` into other languages. |
| **Character art** | Sprites are generated procedurally from `assets/character/generator/`. New states or expressions are welcome. |

You don't need to ask permission for small fixes. For a new adapter or anything that changes
behaviour, open an issue first so we can agree on scope before you spend an evening on it.

## Reporting a false positive

A diagnostic tool lives and dies by how much you can trust it. If Nosy told you something was broken
when it wasn't, that's a bug worth more than most features.

Use the [false positive template](https://github.com/2026osscontest/nosy/issues/new?template=false-positive.yml)
and include:

- **What Nosy said** — the finding title and the file/line it pointed at
- **Why it was actually fine** — the part we got wrong
- **The relevant lines** from your rc file
- **Your setup** — macOS version, shell (`echo $SHELL`), and any version managers you use

> [!IMPORTANT]
> **Redact before you paste.** Shell rc files collect API keys, tokens, and internal hostnames over
> time. Replace them with `REDACTED` — we only need the lines relevant to the finding, not your whole
> config.

## Development setup

Requires **Node 24+**, **pnpm 11**, and **macOS 12+**.

```sh
git clone https://github.com/2026osscontest/nosy.git
cd nosy
pnpm install

# apps/pet links against packages/core's dist/, which git checkout doesn't include.
# Build core first or the app won't start and its tests won't run.
pnpm --filter @nosy/core build

pnpm --filter @nosy/pet dev
```

**Run the app from a terminal during development, but test packaged builds from Finder.** The two
environments differ: an app launched from Finder inherits a minimal `PATH` with no `~/.local/bin` or
`/opt/homebrew/bin`. Nosy works around this by asking your login shell for its `PATH` at startup
(`apps/pet/main/login-path.ts`), and that code path only gets exercised in the Finder case. Bugs of
this shape are invisible to `pnpm dev`.

### Testing against a fake home directory

Diagnosing your real shell config while developing is noisy and risky. `scripts/` sets up a
throwaway home:

```sh
HOME="$PWD/.demo-home" pnpm --filter @nosy/pet dev
```

## Project layout

```
packages/core/       The diagnostic engine. No Electron, no UI, no direct filesystem access.
  src/adapters/        One file per adapter
  src/host.ts          DiagnosticHost — the single seam to the outside world
  src/types.ts         Finding, AdapterResult, Severity, …
  src/score.ts         Health score calculation (pure)
  src/snapshot.ts      Snapshot storage and drift comparison
  src/cli.ts           Internal development tool. Not a product — please don't document it as one.

apps/pet/            The Electron app.
  main/                Main process: window, tray, IPC, scheduler
  renderer/            React UI. PetView.tsx is the only file that draws the pet.
  shared/              Types shared across the IPC boundary

docs/                The source of truth. specs/ holds one spec per feature; ADR.md holds decisions.
assets/              Character sprites and the app icon, both generated by scripts.
```

## Writing a new adapter

This is the most likely thing you'll want to add, so here is the whole path. An adapter's job is to
look at one tool or one area and return `Finding[]`.

### 1. Write the spec first

Add `docs/specs/adapter-<name>-spec.md`. Look at
[`adapter-shell-rc-spec.md`](docs/specs/adapter-shell-rc-spec.md) for the shape: numbered functional
requirements (`FR-001`, …) and the reasoning behind judgement calls. This is where you decide what
counts as a problem — do it before writing code, not after.

### 2. Implement against `DiagnosticHost`, never against the machine

```ts
import type { Adapter, DiagnosticHost, Finding } from '../types.js'

export function createMyAdapter(): Adapter {
  return {
    name: 'my-tool',
    kind: 'wrapping', // 'self' = Nosy's own checks, 'wrapping' = wraps another tool's diagnostics

    // Return a reason string to skip when the tool isn't installed. Skipped adapters
    // deduct nothing from the score — absence is not a problem.
    async skipReason(host) {
      const { code } = await host.exec('which', ['my-tool'])
      return code === 0 ? null : 'my-tool이(가) 설치되어 있지 않습니다'
    },

    async run(host): Promise<Finding[]> {
      const content = await host.readFile(`${host.homedir}/.my-tool-rc`)
      if (content === null) return []
      // …
    },
  }
}
```

**Never import `node:fs` or `node:child_process` inside an adapter.** Everything goes through `host`.
This isn't style preference — it's what makes the next step possible.

### 3. Test with `FakeHost`

Because the adapter only talks to `host`, you can describe an entire machine as a literal:

```ts
const host = new FakeHost({
  homedir: '/Users/test',
  files: { '/Users/test/.my-tool-rc': 'broken line here' },
  execResults: { 'which my-tool': { stdout: '/usr/bin/my-tool', stderr: '', code: 0 } },
})

const findings = await createMyAdapter().run(host)
expect(findings).toHaveLength(1)
expect(findings[0].evidence).toEqual({ file: '/Users/test/.my-tool-rc', line: 1, excerpt: 'broken line here' })
```

No temp directories, no mocking the filesystem, no "works on my machine".

### 4. Register it

Add it to `ADAPTERS` in `packages/core/src/run.ts` and export it from
`packages/core/src/index.ts`.

### 5. Checklist before you open the PR

- [ ] `docs/specs/adapter-<name>-spec.md` exists and matches what the code does
- [ ] The adapter reads and executes **only** through `DiagnosticHost`
- [ ] `skipReason` returns a reason when the tool isn't installed
- [ ] Every finding has either `evidence` (file/line/excerpt) or `fix.command` — see
      [below](#what-makes-a-good-finding)
- [ ] No finding proposes a destructive fix
- [ ] Tests use `FakeHost` and cover the "nothing is wrong" case, not just the failure cases
- [ ] Registered in `run.ts` and exported from `index.ts`

## Rules that aren't up for debate

These come from [`docs/ADR.md`](docs/ADR.md), where each has a recorded rationale. A PR that breaks
one will be asked to change, so it's cheaper to know them going in.

- **Two deployable targets: `packages/core` and `apps/pet`.** Not three. New functionality goes into
  one of the two. (ADR-005)
- **Adapters receive `DiagnosticHost`.** No adapter touches the filesystem or shell directly. (ADR-006)
- **`<PetView>` is the only component that draws the pet.** The 2D→3D swap must stay a
  one-file change. (ADR-001)
- **`packages/core/src/cli.ts` is an internal development tool.** Don't turn it into a product or
  document it as one. (ADR-005)
- **Drift comparison is scoped to the adapters that actually ran.** A partial scan must never diff
  against the full set of finding IDs, or every unscanned adapter looks like it was fixed. (ADR-007)
- **The stack is TypeScript throughout.** Rust/Tauri was evaluated and rejected. (ADR-003)

`docs/ADR.md` also has a **"재논의 금지 항목"** (settled questions) table. Those were decided
deliberately; reopening them needs new information, not a fresh opinion.

## What makes a good finding

```ts
{
  id: 'shell-rc:/Users/me/.zshrc:missing-source:/Users/me/.nvm/nvm.sh',
  adapter: 'shell-rc',
  severity: 'error',
  title: '존재하지 않는 파일을 source하고 있습니다',
  cause: '"/Users/me/.nvm/nvm.sh" 파일이 존재하지 않아 셸 시작 시 오류가 발생할 수 있습니다.',
  evidence: { file: '/Users/me/.zshrc', line: 42, excerpt: 'source ~/.nvm/nvm.sh' },
  fix: {
    description: '더 이상 존재하지 않는 파일에 대한 source 구문을 제거하세요.',
    edit: { file: '/Users/me/.zshrc', removeLine: 42, expectedLine: 'source ~/.nvm/nvm.sh' },
  },
}
```

**Evidence or a command — never neither.** If the problem comes from a file, give the path, the line
number, and the original text. If it doesn't, give a command the user can run. A finding that only
describes a symptom is not finished.

**IDs must be stable across runs.** Drift detection compares IDs between snapshots. An ID containing
a timestamp, a random value, or an array index makes every run look like a brand-new problem.

**Prefer a miss to a false alarm.** When you can't determine whether something is really broken —
a `PATH` entry built from an unexpanded variable, an alias pointing at a shell function — skip it.
`isUnresolvable()` in `shell-rc.ts` exists for exactly this.

**Severity means something.** `error` deducts 15 points, `warn` deducts 5. Use `error` when the shell
or tool is actually misbehaving, `warn` for things that are untidy but working.

**Fixes stay reversible and non-destructive.** Deleting files or packages and resetting global
configuration are excluded from fixes entirely. If a fix can't be undone, leave `fix.revert` unset so
the UI can disable the undo button rather than imply something it can't deliver. (ADR-008)

## Tests and linting

```sh
pnpm test    # both packages
pnpm lint
pnpm build
```

CI runs all three on macOS for every push and pull request. Please make sure they pass locally first —
the macOS runner is slower to queue than a Linux one.

Two things worth knowing:

- **Check that a new test doesn't contradict an existing one in the same `describe`.** This has
  actually bitten us: a new drift baseline rule was added that directly conflicted with an existing
  ID-scoping test, and the conflict wasn't visible until both ran.
- **Test the quiet case.** An adapter that finds problems correctly but also fires on a healthy
  machine is worse than no adapter.

## Commits and pull requests

Commits follow [Conventional Commits](https://www.conventionalcommits.org/):

```
feat(core): docker 어댑터를 추가한다
fix(pet): GUI로 띄운 앱이 로그인 셸 PATH를 잃던 문제를 고친다
docs: 새 어댑터 작성 절차를 추가한다
```

Korean or English are both fine for the message body. What matters is that it explains **why**, not
just what — the diff already says what.

For pull requests:

1. Fork and branch off `master`.
2. Keep it to one concern. An adapter and a UI refactor in one PR is two PRs.
3. Make sure `pnpm test`, `pnpm lint`, and `pnpm build` pass.
4. If you changed adapter behaviour, update the matching `docs/specs/` file in the same PR. The specs
   are the source of truth; code that drifts from them is the thing that's wrong.
5. Fill in the PR template.
