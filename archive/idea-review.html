그래서 뭐가 문제인가

한국어는 어절(띄어쓰기) 단위로 줄을 바꾸는 게 표준 조판입니다. 유니코드 표준 알고리즘(UAX#14)의 기본값은 한글을 중국어·일본어와 같은 부류로 취급해 글자마다 줄바꿈을 허용하고, 그래서 한국 개발자들은 word-break: keep-all을 CSS에 필수로 넣습니다.

문제는 브라우저 밖입니다. OG 이미지 생성, 화면 캡처, PDF 변환, 터미널 출력, 조판 엔진 — 이쪽 텍스트 레이아웃 스택에는 그 처리가 사실상 전무합니다. 브라우저에서는 멀쩡한 문장이 이미지로 뽑으면 단어 한가운데서 잘립니다.

원인을 코드 라인까지 특정했습니다

가장 널리 쓰이는 css-line-break를 직접 설치해 돌려봤습니다.

같은 옵션이 중국어에서는 되고 한글에서는 완전히 무시됩니다. 원인은 LineBreak.ts 555–560행입니다.

const forbiddenBreakpoints =
    options.wordBreak === 'keep-all'
        ? isLetterNumber.map((letterNumber, i) => {
              return letterNumber &&
                  codePoints[i] >= 0x4e00 && codePoints[i] <= 0x9fff;
          })
        : undefined;

저 범위는 CJK 통합 한자만입니다. 한글 음절도, 자모도, 가나도 빠져 있습니다. 작성자가 "CJK = 한자"라고 생각하고 하드코딩한 것이고, 2018년부터 방치돼 있습니다. 고치는 건 코드 네댓 줄입니다.

왜 아직 아무도 안 했나

이건 라이브러리 버그가 아니라 한국어를 아는 사람에게만 보이는 결함입니다. 진입장벽이 우리가 아니라 남에게만 높습니다.

검색으로 반증을 시도했지만 전부 실패했습니다. npm의 korean-linebreak·hangul-linebreak 같은 이름은 전부 404이고, GitHub 검색 결과도 0건이며, 심지어 이 문제로 이슈가 신고된 적조차 없습니다. 한국인 사용자가 깨지는 건 봤어도 원인을 라이브러리까지 역추적하지 못한 겁니다.

"유니코드 최신 구현(ICU4X)으로 갈아타면 해결된다"는 통념도 반례가 있습니다. Typst #1164는 별 5.5만짜리 조판 엔진에서 3년째 미해결이고, ICU4X로 전환한 뒤에도 한국어는 그대로 깨집니다. ICU4X 본진도 #8047에서 "현재 구현이 꽤 조잡하고 스펙 자체가 세부가 부족하다"고 인정하고 있습니다.

업스트림에 머지가 안 돼도 출품작이 성립하도록 설계했습니다. css-line-break는 2023년 9월 이후 커밋이 없어서 이 안전장치가 필요합니다.

지금 벌어지는 일

llama.cpp는 별 12만짜리 로컬 LLM 추론 엔진입니다. 브라우저에서 돌리는 WebGPU 백엔드가 있는데 아직 절반만 완성돼 있습니다. 제가 공식 지원 행렬을 직접 받아 세어봤습니다.

비어 있는 연산자 때문에 RWKV 계열, 음성 모델, 임베딩 모델이 브라우저에서 GPU를 못 쓰고 CPU로 떨어집니다.

왜 이게 견고한가

빈칸을 프로젝트 자신이 공개하고 있습니다. docs/ops.md는 스크립트로 자동 생성되는 공식 미구현 목록이라, "사실은 이미 있었다"가 원천적으로 불가능합니다. 추적 이슈는 1년 넘게 열려 있고 담당자가 없으며, 열린 PR 중 연산자 구현은 0건입니다.

세 가지가 동시에 성립합니다. GPU가 필요 없고(공식 CI에 macos-latest 잡이 있어 맥북 내장 GPU로 개발·검증됩니다), 정확성 증명이 구조에 내장돼 있고(테스트가 CPU 구현을 정답지로 수치 비교), 연산자 하나 = PR 하나라 중간에 멈춰도 성과가 남습니다.

왜 2위인가

활용성 11점. 우리가 만든 것이 업스트림에 흡수되는 구조라 "남이 우리 걸 설치해서 쓴다"는 증명이 간접적입니다. 데모 앱과 커버리지 대시보드는 부수적 자산이고, 1위처럼 npm install 한 줄로 도입되는 물건이 아닙니다.

zephyr-embedded-hal

Zephyr RTOS에서 기존 Rust 드라이버를 그대로 쓸 수 있게 하는 어댑터

66.2탈락

발표 카피는 셋 중 가장 강했습니다

"embedded-hal 생태계의 드라이버 1,704개와 Zephyr의 보드 1,090개 사이에는 어댑터 한 장이 없어서 곱이 0이었습니다. 우리가 그 한 장을 만들었습니다."

빈칸도 진짜입니다. 공식 Rust 모듈에 구현된 디바이스는 gpio.rs, flash.rs 단 둘이고, 어댑터를 요청한 이슈 #73은 17개월째 방치돼 있으며 관련 PR은 0건입니다. 비어 있는 이유가 "어려워서"가 아니라 메인테이너 1인 병목이라 우리에게 유리한 조건이었습니다.

탈락 사유 — 실행 리스크 단 하나

원점수는 90점으로 2위였습니다. 그런데 Rust + unsafe FFI + Zephyr 빌드 시스템까지 2주 안에 동시에 익혀야 합니다. 팀에 Rust 경험자가 없다고 확인돼 실행 리스크 계수를 0.70으로 적용했고, 90 → 66.2가 됐습니다.

루브릭 기준으로 "새로 배울 것이 2개 이상"이면 그 아이디어는 이미 진 것으로 봅니다. 1라운드에서 원점수 상위 3개의 격차가 7점이었는데 최종 격차가 12.3점으로 벌어진 것도 같은 이유였습니다.

1라운드에서 배운 것

지난번 후보 8건 중 상위 4건이 이미 존재하는 것이었습니다. MCP 컨포먼스 도구는 공식 저장소가 있었고, 에이전트 관측 도구는 Claude Code가 이미 내장했고, 스킬 보안 검사기는 다섯 개가 나와 있었고, 공공 API 생성기도 이미 있었습니다. 전부 트렌드 기사만 읽고 "빈틈"이라고 판단한 결과였습니다.

표준의 검증기는 공식 진영이 직접 만든다

규격을 관리하는 조직은 컨포먼스 테스트를 반드시 스스로 만듭니다. 규격 검증 도구는 구조적으로 공식 진영과 충돌합니다.

인기 도구의 어댑터는 호스트가 내장한다

붙이려는 대상이 그 기능을 직접 흡수하면 어댑터는 존재 이유가 사라집니다. 공식 문서를 먼저 읽어야 합니다.

신생 생태계의 보안 스캐너는 상용 벤더가 즉시 진입한다

"채택 속도가 보안 도구 성숙을 앞질렀다"는 서술은 대개 사실이 아닙니다. 보안은 가장 빨리 따라붙는 영역입니다.

그래서 2라운드는 코드베이스 안쪽을 노렸다

외부에서 감싸는 도구가 아니라 프로젝트 내부에 실제로 비어 있는 자리입니다. 공식 진영과 경쟁하는 게 아니라 그 일부가 되므로 같은 방식으로 죽지 않습니다. 2025년 금상작(Zephyr RTOS 포팅 + 교육자료)이 정확히 이 형태였습니다.

팀에서 정할 것

A · 1위로 확정

한글 줄바꿈. 파급력·서사·데모·한국 맥락이 모두 1위이고 학습 부담이 가장 낮습니다. 약점은 혁신성 한 항목입니다.

B · 2위로 확정

기술적 견고함과 "별 12만 프로젝트에 머지된 PR"이라는 이력을 우선한다면. 맥북이 있어 실행은 가능합니다.

C · 1위 + 곁다리 PR

한글 줄바꿈을 본체로 하고, axe-core #5308(접근성 검사기가 CJK 문장부호를 빠뜨려 한국어 페이지에서 오탐)을 보조로 추가. "서구 기본값이 CJK를 빠뜨린다"는 같은 서사를 접근성까지 확장합니다. 비용 반나절.

결정 기한

D-10입니다. 착수가 늦어질수록 코퍼스 규모와 업스트림 PR 수가 줄어듭니다. 오늘 안에 정하는 것이 안전합니다.
