# 후보 A — `carveout`

## 1. 한 문장 정의

거대한 Python 코드베이스에서 모듈 하나를 지목하면, 의존 심볼 그래프를 역추적해 **필요한 파일·테스트만 골라내고 순환 의존을 끊어, `pip install` 가능하고 테스트가 통과하는 독립 패키지를 60초 안에 만들어 내는 도구.**

## 3. 시간 단축 배율

**현재 수작업 (근거)**
- 실무에서 "이 모듈 라이브러리로 떼자"는 작업은 ① 어떤 파일이 딸려 오는지 손으로 import 추적 ② 상위 모듈을 역참조하는 순환 의존 발견·절단 ③ 관련 테스트만 골라내기 ④ `pyproject.toml`·의존성 목록 작성 ⑤ 빌드/테스트 반복 수정으로 구성된다.
- [확인] 업계 통설: "작은 독립 라이브러리를 떼는 것이 훨씬 쉽고, 의존성 있는 큰 기능은 그것이 의존하는 코어 라이브러리 전부를 먼저 떼지 않으면 추출할 수 없다" (https://pavelkorolev.xyz/blog/2023-06-28-breaking-monolith-step-by-step/) — 즉 ②가 실무의 병목임이 문헌으로 확인된다.
- [추정] 300~1,000 파일 규모 저장소에서 중간 크기 모듈 1건 추출 = **8~24 실무 시간(1~3일)**. 근거: import 역추적이 파일 수에 선형이고, 순환 의존 1건당 판단·수정에 30분 이상 소요.

**자동화 후**: 그래프 구축 3~10초 + 파일 복사·리라이트 2초 + 테스트 1회 실행 20~40초 = **60초 이내**.

**배율 ≈ 500~1,500배.** 정직하게 말하면 "완벽한 결과"가 아니라 "사람이 2시간 걸려 만들 초안을 60초에 만들고, 통과 여부를 기계가 판정"이다. 발표에서는 이 단서를 붙이는 것이 QA 방어에 유리하다.

## 6. 2주 실현성

- **v0 언어: Python 100%.** 대상도 Python 코드베이스. 2주 완주를 위한 최소 범위.
- **활용 오픈소스**: `grimp`(import 그래프) + `libcst` 또는 `ast`(코드 리라이트) + `uv`(격리 빌드·테스트) + `networkx`(최소 절단 계산). 자체 개발은 오케스트레이션과 절단 전략에 집중 → 대회 "오픈소스SW 적절성" 10점 확보 구조.
- **언어 제약 정정으로 열린 확장 경로 (선택)**: 심볼 그래프 추출을 **tree-sitter**로 바꾸면 TypeScript·Go·Java·C++까지 동일 알고리즘이 적용된다. 이건 단순한 기능 추가가 아니라 **"우와" 체크리스트 2번의 사정거리를 바꾼다** — "Python 저장소를 말씀해 주세요"가 "**아무 저장소나 말씀해 주세요**"가 되면 현장 체험의 임팩트가 질적으로 달라진다.
  - 다만 **2주 안에는 Python + TypeScript 2개 언어까지만** 목표로 하고, tree-sitter 어댑터 인터페이스를 열어두어 "언어 추가는 커뮤니티 기여 포인트"로 제시하는 것이 안전하다 (커뮤니티 확장 가능성 10점에도 유리).
  - 성능이 필요하면 그래프 추출부만 Rust로 빼는 것도 이제 허용 범위지만, **공수 대비 이득이 없으므로 권하지 않는다.** 병목은 그래프 계산이 아니라 테스트 실행 시간이다.
- **미지 요소 3개**: ⓐ 순환 의존 자동 절단 전략(Protocol 주입으로 치환)의 성공률 ⓑ 동적 import·`__init__` 부작용 처리 ⓒ 테스트 선별 정확도.
- **리스크 완화**: v0 범위를 **"추출 초안 + 통과/실패 판정"**으로 못 박고, 실패 시 사람이 무엇을 고쳐야 하는지 리포트를 낸다. "완전 자동"을 약속하지 않는 것이 2주 안에 데모를 성립시키는 유일한 길이다.

- 재현 가능한 벤치마크: 실제 OSS 저장소 10곳에 대한 추출 성공/실패 로그 (대회 이후에도 커뮤니티가 늘려갈 수 있는 자산).

- **정직한 판정**: 현재 에이전트는 742파일 규모에서 import 그래프를 놓쳐 실패한다(컨텍스트 한계·정확한 심볼 추적 불가). 결정론적 그래프 도구가 명확히 우세하다. **다만 3년은 낙관적이지 않다. 1~2년.**
- **완화 각도**: 이 도구를 **에이전트가 호출하는 결정론적 백엔드**(MCP 서버 겸용)로 포지셔닝하면 에이전트 발전이 위협이 아니라 수요가 된다. 발표에서 이 프레이밍을 반드시 쓸 것.

# 후보 B — `bytespec`

## 1. 한 문장 정의

국내 금융·세무·관세 시스템의 **고정길이 전문(電文) 규격서(HWP·엑셀·PDF)를 넣으면 필드 오프셋·타입·코드값을 자동 추출해 파서·빌더 코드와 왕복 검증 테스트를 생성하고, 실제 전문 바이트를 붙여넣으면 필드 단위로 실시간 해독해 보여주는 도구.**

## 3. 시간 단축 배율

- **현재 수작업** [추정]: 필드 300개 규격서 1건 → 오프셋·길이 전사(3~4시간) + 파서/빌더 코드 작성(4~6시간) + 오프셋 1칸 오류 디버깅(3~6시간). 합 **12~16시간**. 오프셋 오류는 증상이 "엉뚱한 필드에 값이 들어감"으로 나타나 디버깅이 비정상적으로 길다는 것이 이 도메인의 특징.
- **자동화 후**: 문서 파싱 5초 + 코드 생성 2초 + 샘플 전문 왕복 검증 3초 = **30초 이내**.
- **배율 ≈ 1,500~2,000배.**

## 6. 2주 실현성

- **언어: Python(문서 파싱·코드 생성) + TypeScript(hex 뷰어).** 팀 제약 일치.
- **활용 오픈소스**: HWPX 파서(HWPX는 KS 표준 오픈 XML — `hwp-hwpx-parser` 등 순수 Python 파서 실존 https://github.com/KimDaehyeon6873/hwp-hwpx-parser), `openpyxl`, `pdfplumber`, `jinja2`(코드 생성), `pydantic`.
- **AI 의존도**: 기본 경로는 **규칙 기반 결정론적** 표 해석 → 규정 제9조 리스크 0. 표 헤더 의미 매핑이 애매한 경우에만 **오픈웨이트 소형 모델(Qwen3-4B급, 맥북 로컬)** 을 옵션 보조로 사용. 모델 없이도 전 기능 동작하는 구조로 설계.
- **미지 요소 4개** (A후보보다 많음): ⓐ 규격서 표 레이아웃의 다양성(기관마다 다름) ⓑ HWP 5.0 바이너리 대응 범위 ⓒ 실제 샘플 전문 확보(규격서만 있고 샘플이 없으면 왕복 검증 데모가 약해짐 → 생성기로 합성 전문 제작) ⓓ 인코딩(EUC-KR/CP949 혼용, 한글 2바이트가 고정길이 계산에 미치는 영향 — 이 도메인의 실제 버그 원천이라 **오히려 세일즈 포인트**).
- **리스크**: 공개 규격서 2~3종에만 확실히 동작해도 데모는 성립한다. 범용성을 약속하지 말고 "규격서 형태를 프로파일로 확장하는 구조"로 제시.

## 7. 대표 저장소에 남는 것

- `bytespec` CLI + 웹 hex 디코더, **기관별 규격서 프로파일**(관세청/국세청 등) — 커뮤니티가 프로파일을 추가 기여하는 구조가 자연스럽다.
- 국내 공개 전자문서 규격을 기계 판독 스키마로 축적한 **오픈 스키마 저장소**. 대회 이후 실제 공공 자산이 된다.

## 8. 정량 지표

1. 규격서 필드 추출 정확도 (사람이 만든 정답 대비 precision/recall)
2. 왕복 검증(parse→serialize) 바이트 동일률
3. 규격서 1건당 코드 생성 시간
4. 지원 규격 프로파일 수
5. 사람 확인 요청(warning) 비율 — 낮을수록 좋음, 숨기지 않는 것이 신뢰

## 9. 수명 판정 — ✅ **A후보보다 강함**

- 국내 금융·세무·관세의 고정길이 전문은 **3년 뒤에도 확실히 존재한다**. 이 레이어는 20년째 교체되지 않았고 교체 계획도 없다.
- **AI 에이전트 대체 위험 낮음**: ⓐ HWP 바이너리를 LLM이 직접 읽지 못한다 ⓑ 오프셋 정확도는 확률적 생성이 가장 취약한 영역이며 1바이트 오류가 치명적이다 ⓒ 규격서가 대외비인 경우 상용 API에 올릴 수 없다 — **로컬 결정론적 도구여야 하는 구조적 이유가 있다.**
- 이 후보는 오히려 **에이전트 시대에 수요가 커지는** 쪽이다.

# 최종 권고

1. **후보 A(`carveout`)를 1순위로 제안한다.** 이유는 "우와" 점수가 아니라 **체크리스트 2번(현장 체험)** 이다. 심사위원이 임의의 저장소를 부르면 즉석 실행되는 데모는 이 팀이 지금까지 검토한 어떤 후보도 갖지 못한 방어력이다. 15분 발표의 5분 QA를 무기로 바꾼다.
2. **후보 B(`bytespec`)는 "우와" 절대치와 수명·한국 가산점에서 A를 이긴다.** 시각 효과가 연출이 아니라 기능 자체이고, AI 에이전트 대체 위험이 구조적으로 낮다. **만약 팀이 2일 안에 공개 규격서 2종 + 샘플 전문을 실제로 확보할 수 있다면 B를 1순위로 올려야 한다.** 확보 실패 시 즉시 A로 회귀.
3. **A의 유일한 치명 약점은 수명(1~2년)** 이다. 반드시 "AI 에이전트가 호출하는 결정론적 백엔드(MCP 겸용)"로 포지셔닝해 이 질문을 선제 방어할 것.
4. 두 후보 모두 **AI 모델이 필수 경로에 없다** → 대회 규정 제9조 실격 리스크 0. 이 축에서 이건 드문 자산이다.
5. 이 축에서 **글로벌 범용 개발자 도구는 더 파지 말 것을 권고한다.** 9개 방향 중 7개가 즉사했고, 남은 2개도 한쪽은 한국 특수성으로, 다른 한쪽은 "린터는 많은데 실행기는 없다"는 좁은 틈으로 겨우 생존했다.
