## 확정된 아이디어: 개발 환경 진단 펫 (Dev Env Doctor Pet)

**한 문장 정의**: 여러 개발 도구의 개별 진단(doctor) 결과를 하나로 모으고, 문제가 있으면 "정확히 어디서 어떻게 고치는지"를 안내하는, 화면 위에 투명한 창으로 직접 돌아다니며 상주하는 펫 (메뉴바/트레이 아이콘 아님 — Shimeji·데스크톱 버디 스타일).

**풀려는 문제 (4가지, 순서대로 우선순위)**
1. `flutter doctor` 같은 도구가 "무엇이 문제인지"는 말해줘도 "어느 파일 몇 번째 줄을 고쳐야 하는지"는 안 알려준다 — 증상→원인 파일:줄 번호→고치는 명령어로 번역
2. `brew doctor`/`flutter doctor`/`npm doctor`가 각자 따로 존재하고 존재 자체를 모르는 사람이 많다 — 설치된 도구를 자동 감지해 관련 doctor를 다 돌리고 하나의 헬스 스코어로 통합
3. PATH 충돌, 죽은 alias, 고아 환경변수처럼 서서히 환경이 망가지는 문제("works on my machine"의 원인)를 잡아준다
4. (2차 서사) 코딩 에이전트가 막히는 이유의 상당수가 코드 버그가 아니라 환경 문제 — 작업 전에 "이 프로젝트 돌릴 준비 됐는지" 미리 확인 가능

**핵심 차별점**: 새 기술을 발명하지 않는다. 이미 흩어진 개별 진단 능력(`brew doctor`, `flutter doctor`, `shellrc-doctor` 등)을 어댑터로 결합하는 것 자체가 가치.

**어댑터 v1 후보 목록** (대화 중 예시로 나온 것, MVP에 몇 개 넣을지는 인터뷰에서 확정): Python(pyenv/poetry 충돌), Ruby(rbenv/bundler 불일치), Docker(데몬 실행 여부), Git(전역 config·SSH 키), VS Code(`extensions.json` 권장 확장 미설치), Rust(rustup 툴체인). 여기에 `brew doctor`/`flutter doctor`/`shellrc-doctor` 래핑 어댑터가 기본으로 추가됨.

## 미해결 — 다음 세션에서 반드시 논의할 것: 3D 캐릭터

사용자가 원래 원했던 것도, 다시 확인한 것도 **PokoPet 같은 3D 캐릭터**임. 이건 아직 결론이 안 났고, 다음 세션에서 반드시 정면으로 다뤄야 함.

- **채점과는 무관한 순수 선호/리스크 트레이드오프**임을 먼저 짚을 것 — 루브릭은 2D냐 3D냐를 전혀 평가하지 않음. 순전히 "얼마나 시간/리스크를 들여서라도 원하는 비주얼을 가질 것인가"의 문제
- OpenPets 실사 결과 2D 스프라이트 애니메이션 기반으로 보임(3D/WebGL 언급 없음, `pet-format` 패키지 스펙까지는 확인 안 함) → **Plug-in(B) 경로로는 3D가 안 될 가능성이 높음**
- 검토할 옵션:
  - **옵션 1**: `pet-format` 패키지 스펙을 실제로 열어서 커스텀 렌더러(예: 캔버스에 three.js 임베드) 허용 여부 재확인 — 만약 된다면 OpenPets 위에서도 3D 가능
  - **옵션 2**: Build(A)로 가서 Electron/Tauri 안에 three.js/Babylon.js로 직접 3D 렌더링 — 완전한 통제권, 대신 진단 스케줄링·패널 UI 등도 전부 직접 구현해야 해서 빌드 공수 크게 증가 (D-11 안에 가능한지 팀 스택과 함께 냉정히 판단 필요)
  - **옵션 3**: 이번 대회는 2D로 안전하게 제출하고, 3D는 대회 이후 사이드 프로젝트로 발전시키기
- 이 논의의 결과가 Build vs Plug-in 최종 결정, Electron vs Tauri, 전체 타임라인에 전부 연쇄적으로 영향을 주므로 **다른 세부 사항보다 먼저 결론 내는 게 좋음**

**중요한 설계 결정 1 (확정)**: 이 도구를 "새 머신 세팅할 때 한 번 쓰는 온보딩 도구"로만 두면, 펫이 대부분의 시간 동안 아무 기능도 안 하는 죽은 캐릭터가 된다는 문제가 지적되어 방향을 수정함.
→ **핵심 가치를 "온보딩"에서 "지속적 드리프트 감지"로 이동.** 마지막 정상 스냅샷과 주기적으로 비교해서 "어제까지 되던 게 오늘 안 됨"을 즉시 알림.
→ 이 설계가 확정 전제이므로 "일회성 도구로 되돌릴지" 재논의하지 말 것.

**중요한 설계 결정 2 (확정)**: 처음엔 셸 프롬프트(터미널 텍스트) → 메뉴바 트레이 아이콘까지 검토했으나, "PokoPet처럼 화면 자체에 실체감 있게 상주해야 한다"는 지적으로 **투명·항상 위·프레임 없는 오버레이 창으로 화면에 직접 떠 있는 크로스플랫폼 데스크톱 펫(Electron 또는 Tauri)으로 확정**함. 트레이 아이콘 방식은 폐기.
- 화면 위를 캐릭터가 돌아다니거나 한 자리에 앉아있고, 상태에 따라 스프라이트/애니메이션 교체(정상일 때 평온, 문제 발견 시 걱정하는 모션)
- 이 장르는 이미 잘 정립되어 있어 빌드 리스크가 낮음 — 참고 가능한 오픈소스: OpenPets, Shijima-Qt, Desktop Virtual Buddy (Electron+TS 기반)
- 백그라운드에서 진단 엔진(코어+어댑터)을 주기적으로 호출해 스냅샷과 비교 — CLI로 설계했던 진단 로직 자체는 그대로 재사용, 얼굴(프레젠테이션 레이어)만 교체
- 클릭하면 근처에 말풍선/작은 패널로 문제 목록과 고치는 법 표시
- **핵심 결정 필요 — Build vs Plug-in**: 펫 렌더링·이동 애니메이션을 처음부터 직접 만들지(A), 아니면 이미 "로컬 우선 데스크톱 펫 플랫폼 + 플러그인 SDK"를 표방하는 **OpenPets**에 우리 진단 로직을 플러그인으로 얹을지(B) 인터뷰에서 확정. B가 빌드 공수를 크게 줄이고 "기존 OSS 결합"이라 2-5(OSS 적절성) 점수에도 유리함.
  - **OpenPets 라이선스 확인 완료**: MIT (GitHub API로 검증, `github.com/alvinunreal/openpets/blob/main/LICENSE`). 가져다 쓰고 수정·재배포·상업적 이용까지 자유로움, 원저작권 고지만 유지하면 됨 — Build vs Plug-in 결정에서 라이선스는 더 이상 장애물 아님
  - 미확인 남은 것: OpenPets의 트랜지티브 의존성(그 안이 쓰는 다른 패키지들)에 GPL류가 섞여 있는지는 SBOM 작성 시점에 실제 `package.json`을 열어 스캔 필요. 플러그인 SDK 문서화 수준·최근 유지보수 활성도도 아직 미확인이니 인터뷰에서 저장소를 직접 열어 확인할 것

**중요한 설계 결정 3 (확정)**: 초기 아이디어에 "펫이 직접 OS 설정 탭을 열고 클릭해서 고쳐준다"는 요소가 있었음. 실사해본 결과 OpenPets SDK엔 화면 자동화(접근성 API로 실제 OS를 클릭하는) 기능이 없고, 이걸 별도로 만들면 OS 버전마다 깨지기 쉽고 라이브 데모 실패 리스크가 크며, 무엇보다 "일반 사용자의 실제 OS 설정을 대신 조작"이라는 프레이밍은 이미 기각한 "OS 설정 도우미 펫"으로 되돌아가 G1을 다시 건드림.
→ 사용자가 진짜 원한 건 "실제 OS 자동화 기능" 자체가 아니라 **"펫이 뭔가를 조작하는 걸 지켜보는 시각적 재미"**였음이 확인됨.
→ **해결**: 실제 OS 설정 화면을 건드리지 않고, **우리가 완전히 통제하는 자체 UI 패널(스위치/토글 형태로 디자인)** 안에서 펫이 조작하는 애니메이션을 수행. 그 순간 백그라운드에서는 실제 진단 엔진이 진짜 명령(`defaults write`, rc 파일 수정 등)을 실행. 사용자에게는 "펫이 직접 고쳐줬다"로 보이지만 구조적으로는 화면 자동화가 전혀 없어 안전함. OpenPets `ctx.ui`(호스트 렌더링 패널)로 구현 가능.
→ 이 설계가 확정 전제이므로 "실제 OS 접근성 API로 System Settings를 클릭하는 방식"은 재논의하지 말 것.

- **주의**: 코어 엔진(라이브러리) + 펫 앱, 이렇게 배포 타깃을 2개로 유지할 것. CLI를 별도 제품으로 홍보하면 "3개 이상 배포 타깃 = 0점" 함정(루브릭 1-1)에 걸릴 수 있으니 CLI는 내부 개발/테스트용으로만 남길 것
- **주의**: 데모 안정성 루브릭(2-3)은 "터미널 정적 출력"이 만점 앵커라 GUI 앱은 이보다 낮게 잡힘 — 라이브 데모 리스크를 낮추기 위해 화면 녹화본을 백업으로 반드시 준비할 것
- 이 설계가 확정 전제이므로 "트레이 아이콘/터미널 프롬프트 방식으로 되돌릴지"는 재논의하지 말 것. 다만 **Build(A) vs Plug-in(B), Electron vs Tauri, 캐릭터 디자인/애니메이션 상태, 백그라운드 체크 주기·트리거**는 인터뷰에서 확정 필요.

## 이미 검증 완료된 사실 (재검증 불필요)

- **`shellrc-doctor`(github.com/nord342/shellrc-doctor)가 이미 존재** — `.zshrc`/`.bashrc`의 중복 PATH, 죽은 alias, 느린 source, 시작 시간을 진단함. **이걸 재발명하지 말고 어댑터로 흡수/연동할 것.**
- `chezmoi`, `dotbot`, `donnemartin/dev-setup` 등은 전부 "설정을 선언적으로 적용"하는 도구이지, "현재 상태를 진단"하는 도구가 아님 — 이 구분이 우리 차별점의 핵심이므로 발표에서 명확히 할 것
- "여러 도구의 doctor를 하나로 통합하는 aggregator"는 검색상 존재하지 않음 (단, 짧게 재확인 권장)
- **하드 게이트 전부 통과 확인됨** (G1~G8) — 단, 스코프를 "개발 환경/개발 도구"로 계속 좁게 유지해야 함. 일반 OS 설정이나 "개인비서"로 넓히면 G1(소비자 서비스 금지)·G2(레드오션: 개인비서가 레드오션 15종에 명시)로 즉시 기각됨. **이 방향은 이미 검토 후 기각된 결정이니 재논의하지 말 것.**
- 헤드리스 에이전트 호출은 넣더라도 "어댑터 없는 롱테일 도구를 만났을 때의 보조 제안" 용도로만 좁게 — 핵심 메커니즘이 되면 "단일 LLM 호출 래퍼" 안티시그널 + G3(상용 API 종속) 위험
- **OpenPets 실사 결과 (README/SDK 문서 확인 완료)**:
  - 라이선스 MIT 확인됨 (재검증 불필요)
  - Electron 기반 (`apps/desktop`), Node.js 20+/pnpm/TypeScript 워크스페이스 — Plug-in(B) 선택 시 Electron으로 자동 확정, Tauri 논의 불필요
  - 렌더링은 "animation frames" 기반 2D 스프라이트로 보임(3D/WebGL 언급 없음) — **3D 캐릭터(PokoPet 스타일)는 이 경로로는 어려울 가능성 높음**. 3D가 필수면 Build(A)로 가야 함
  - `ctx.schedule`(every/cron/daily 타이머), `ctx.ui`(말풍선/핀 고정 HUD/커스텀 패널), `ctx.pets`(반응 애니메이션)가 이미 SDK에 있어 "상시 드리프트 감지" 기능 구현에 딱 맞음 — 새로 만들 필요 없음
  - MCP 통합 레이어가 이미 있어(`openpets_react`, `openpets_say` 등) 코딩 에이전트가 로컬 트리거로 펫을 반응시킬 수 있음 — 우리 진단 엔진도 같은 패턴으로 연결 가능
  - **미확인 (다음 세션에서 `docs/` 폴더로 반드시 검증)**: 플러그인이 샌드박스 안에서 도는데(`ctx.commands`/`ctx.system`), 실제로 `brew doctor` 같은 셸 명령 실행이나 `.zshrc` 파일 읽기가 허용되는지. 이게 막혀 있으면 Plug-in(B) 경로 자체가 우리 핵심 기능(진단 어댑터)을 못 돌릴 수 있어 Build(A)로 전환해야 함

원점수 75/100 추정, 조정계수(R×S×L) 적용 시 약 65~71점 (판정: 기각~보류 경계). **85점을 넘기려면 아래 3개 레버가 필요:**

2. **실제 커뮤니티 접점 만들기**: `shellrc-doctor`에 실제 이슈/PR 남기기, 또는 특정 언어 생태계 온보딩 문서에 레퍼런스 제안 → 커뮤니티 확장(2-4) 점수 견인
3. **기능테스트를 fixture 기반으로 자동화**: 실제 OS 상태에 의존하지 않고 도커 등으로 재현 가능하게 설계 → 기능테스트(2-6) 점수 견인

## 이번 세션에서 인터뷰로 확정해야 할 것

한 번에 다 묻지 말고, 아래 순서로 하나씩 대화하듯 물어보세요.

1. **팀 구성**: 몇 명이고, 각자 익숙한 스택은 무엇인가 (특히 JS/TS vs Rust 경험, 3D 렌더링(three.js 등) 경험 — Build/Plug-in 및 Electron/Tauri 선택의 결정 요인)
2. **3D 캐릭터 논의 (최우선)**: 위 "미해결" 섹션의 3개 옵션 중 확정 — `pet-format` 스펙 재확인(옵션 1) 결과에 따라 Build(A) vs Plug-in(B)이 갈림. 라이선스는 이미 MIT로 확인 끝났으니 재확인 불필요, SDK 문서화 수준·유지보수 활성도만 저장소에서 직접 확인
3. **Electron vs Tauri 최종 선택**: 2번 결정 및 팀 Rust 경험 여부에 따라 확정. Plug-in(B) 선택 시 OpenPets가 쓰는 프레임워크를 따라가는 게 자연스러움
4. **데모용 타깃 OS**: 크로스플랫폼 셸은 유지하되, 실제 어댑터/데모는 어느 한 OS(예: macOS)로 좁힐지 확정
5. **어댑터 v1 목록**: 위에서 예시로 든 Python/Ruby/Docker/Git/VS Code/Rust 중 어느 5개를 MVP로 넣을지, 각 어댑터가 정확히 무엇을 체크할지
6. **골든셋 수집 방법**: 팀원 각자의 실제 세팅 경험을 언제·어떻게 모을지 (D1 작업으로 바로 배정)
7. **커뮤니티 접점 실행 여부**: `shellrc-doctor`(그리고 Plug-in 선택 시 OpenPets에도) 이슈를 지금 남길지, 어떤 언어 생태계 온보딩 문서를 타깃할지
8. **온스크린 펫 캐릭터 UI**: 캐릭터 디자인/애니메이션 상태가 몇 종인지(평온/걱정/심각 등), 클릭 시 말풍선·패널에 무엇을 보여줄지, 애셋을 누가 언제 만들지(직접 그림 vs Plug-in이면 OpenPets 애셋 활용)
9. **백그라운드 체크 주기·트리거**: 앱 실행 시 1회 + N분마다 vs 절전 해제 시 vs 수동 버튼 — 배터리/성능 부담 없는 선에서 확정. 스냅샷 저장 위치(로컬 파일)도 함께
10. **패키징/배포 방식**: 데모 당일 설치를 어떻게 시연할지 (서명 없는 빌드 배포, `.dmg` 직접 실행 등) + 화면 녹화 백업 계획
11. **MCP 서버 노출(스트레치 목표) 여부**: 넣을지, D-11 안에 리스크 없이 가능한지, R(실행 리스크) 계수에 미치는 영향 재계산
12. **D-11 타임라인**: 오늘부터 8/27 18:00까지 일자별 작업 분배 (이전 세션에서 제안한 초안 있음 — 펫 앱 패키징 시간까지 포함해 팀 상황에 맞게 조정)
