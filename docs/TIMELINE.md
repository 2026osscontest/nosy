## 실제 가용 시간
| 날짜 | 요일 | 가용 |
|---|---|---|

| 8/20~8/23 | 목·금·토·일 | **각 2~3시간** (일정 있음) |

풀타임은 4일(8/19, 24, 25, 26)뿐이고 주말이 전부 저강도다.

**재배치 원칙 3가지:**
1. **저강도 4일(8/20~23)에는 코딩량이 작고 독립적인 일을 넣는다** — 어댑터는 하나씩 끝나는 단위 작업이라 2~3시간에 맞고, 골든셋 채굴과 보고서 초고는 읽기·쓰기라 저강도 시간에 가장 잘 맞는다.
2. **큰 미지수는 첫날에 제거한다** — 투명·항상 위 창이 실제로 뜨는지가 이 프로젝트 최대의 기술 리스크다. 8/24에 처음 시도해서 실패하면 복구 시간이 없다. D1에 스파이크로 먼저 확인한다.
3. **보고서를 마지막에 몰지 않는다** — 5페이지 중 상당 부분(개발배경·아키텍처·차별성)은 이미 `docs/PRD.md` "문제 정의와 차별점"에 있다. 저강도 시간에 미리 옮겨 쓰고, 제품이 있어야 쓸 수 있는 부분만 남긴다.

## 포기 우선순위 (일정이 밀렸을 때 이 순서로 버린다)
1. `.dmg` 패키징 (소스 빌드가 주 경로 — `docs/SUBMISSION.md` "심사 일정" 참조)
2. 어댑터 5 (docker) — 가장 단순하고 서사 기여도 낮음
3. 펫이 토글로 걸어가는 애니메이션 — 토글 기능만 남기고 생략
4. 어댑터 4 (git)
5. **절대 못 버리는 것:** 어댑터 1·2(차별점), 드리프트 감지(핵심 가치), **영상·보고서·SBOM**(제출 필수)

> 제출물 3종(영상·보고서·SBOM)은 **기능이 아니라 자격 요건**이다. 기능을 하나 더 넣으려다 이걸 놓치면 심사 자체가 성립하지 않는다.

## 작업 진행 원칙 (1인 + 에이전트)
**전제: 코딩은 전량 에이전트에 위임. 사람은 결정권자이자 테이스트 담당. 따라서 병목은 "사람이 에이전트의 작업을 이해하는 속도"다.**

| 사람이 하는 일 | 에이전트가 하는 일 |
|---|---|
| 스코프 결정, 무엇을 뺄지 판단 | 구현 전량 |
| 어댑터별 "이게 진짜 문제인가" 판정 | 테스트 작성 |
| 골든셋 큐레이션 (수집은 위임, 채택은 사람) | 문서 초안 |
| 펫 캐릭터·UX 취향 결정 | 라이선스 스캔 자동화 |
| 영상 구성과 서사 | 보고서 초안 |

**병목 완화 규칙 (반드시 지킬 것):**
1. **하루에 한 덩어리씩.** 여러 모듈을 병렬로 진행하지 않는다. 이해가 병목인데 병렬로 벌리면 이해가 밀린다.
2. **각 덩어리 끝에 사람이 직접 실행한다.** 테스트를 돌려보고, 통과한 테스트 파일을 실제로 읽는다. 읽지 않고 넘어간 코드가 쌓이면 D7 이후 손을 못 댄다.
3. **새 의존성 추가는 사전 승인.** 에이전트가 임의로 라이브러리를 늘리지 않는다. 라이선스 검증(`docs/SUBMISSION.md`) 부담이 그대로 늘어난다.
4. **파일 수를 늘리지 않는다.** 추상화는 실제로 두 번째 사용처가 생겼을 때만 도입한다.
5. **이해가 안 되는 코드는 그 자리에서 되묻는다.** 넘어가지 않는다.

## 시연영상 3분 구성안
| 구간 | 내용 |
|---|---|
| 0:00–0:20 | **문제 제기.** `flutter doctor` 결과를 보여준다. "문제가 있다"고는 하는데 **어디를 고치라는 말이 없다** |
| 0:20–0:35 | 펫 등장. 화면 위에 상주하며 작업을 방해하지 않는 모습 |
| 0:35–1:15 | **통합.** 흩어져 있던 `brew doctor`/`git`/`docker` 등이 하나의 헬스 스코어로. "이런 게 있는 줄도 몰랐던" 진단들이 자동 수집됨 |
| 1:15–2:10 | **핵심 차별점.** 클릭 → 패널 → `.zshrc:47` 원문 발췌와 수정 명령이 그대로 보임. 토글을 켜면 펫이 조작하고 실제로 고쳐짐 |
| 2:10–2:45 | **드리프트 감지.** `.zshrc`를 일부러 망가뜨린다 → 펫이 스스로 알아채고 걱정 상태로 전환 → "어제까지 되던 게 오늘 안 됨"을 즉시 포착 |
| 2:45–3:00 | 마무리 — 기존 오픈소스를 결합했다는 점, 배포 타깃, 향후 계획(MCP·3D) |

> **제출 형식:** 영상은 유튜브 업로드 후 URL만 보고서에 기재한다. 파일 제출 불가(`docs/SUBMISSION.md` 참조). 업로드·처리 시간을 D8 안에 확보한다.

**촬영 안정성:**
- **각 씬을 개별 촬영**한다. 3분 원테이크를 노리지 않는다.
- **고장난 환경을 스크립트로 재현 가능하게** 만든다 (`scripts/demo-setup.sh`). 재촬영 시 같은 상태를 즉시 복원할 수 있어야 한다.
- 촬영은 D8이지만, **D5 시점부터 씬별로 미리 찍어둔다.** 완성 후 한 번에 찍으면 재촬영 여유가 없다.
