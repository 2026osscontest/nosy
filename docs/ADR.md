# Architecture Decision Records

## 철학
1인 + 에이전트 팀. 코딩은 전량 에이전트에 위임하므로 병목은 "사람이 에이전트의 작업을 이해하는 속도"다(`docs/TIMELINE.md` "작업 진행 원칙" 참조). 따라서 리뷰 불가능한 코드 구간을 만들지 않고, 배포 타깃·의존성·파일 수를 늘리지 않는 쪽을 우선한다. 8일 완주(대회 마감)가 다른 모든 품질 목표보다 우선한다.

### ADR-001: 2D 스프라이트 확정, 렌더러 교체 가능하게 설계
**결정**: v1은 2D 스프라이트로 출품한다. 3D는 1차 합격 후 또는 대회 이후.
**이유**: 팀이 1인이고 사람의 이해가 병목인 구조에서 three.js 씬 그래프·애니메이션 믹서·투명 배경 렌더링은 가장 비싼 코드다. 대회 루브릭은 2D/3D를 전혀 평가하지 않으며, **3D에 쓰는 시간은 점수로 환산되지 않는다.** 사용자 본인이 "수상이 우선, 3D는 되면 좋고"로 우선순위를 명시했다.
**트레이드오프**: 시각적 완성도는 3D보다 낮을 수 있다. 이를 완화하기 위해 펫 렌더링을 `<PetView state={...} />` 컴포넌트 하나로 격리해, 3D 전환 시 이 파일만 교체하면 되도록 설계 비용을 지금 지불한다. 이 격리 설계 자체에 드는 추가 비용은 사실상 0이다 — 어차피 나눠야 할 렌더링 로직을 처음부터 한 파일로 모으는 것뿐이다.
**애셋 조달 (갱신, 8/19)**: 최초 계획은 "MIT/CC0 기존 스프라이트를 우선 재사용하고 1차 서면평가 합격 시 자체 캐릭터로 교체"였으나, 대신 자체 캐릭터를 처음부터 코드로 절차적 생성해 채택한다 — CC0 팩을 찾아 심사하는 시간보다 싸고, 출처 고지 의무 자체가 발생하지 않는다(`docs/SUBMISSION.md` "라이선스 체크리스트" 대상 아님). 산출물: `assets/character/`(원본 해상도 PNG·프레임 데이터·생성 스크립트, `assets/character/README.md` 참조). **주의**: §3(ADR-002)에서 기각한 것은 OpenPets의 *플러그인 SDK 경로*이지 *애셋*이 아니다 — OpenPets는 MIT이므로 그 스프라이트 애셋을 가져다 쓰는 것은 코드 경로 채택 여부와 무관하게 자유롭다(단, 위 결정으로 실제 채택 대상은 아니게 됨).

### ADR-002: Electron 앱 직접 구현 (OpenPets 플러그인 경로 폐기)
**결정**: `alvinunreal/openpets`의 플러그인 SDK 경로를 폐기하고 Electron 앱을 직접 만든다.
**이유**: SDK v3를 실사한 결과(검증 출처: `packages/sdk/src/index.ts`, `docs/plugins.md`, `docs/sdk.md`, `docs/pet-format.mdx`) 셸 명령 실행, 임의 파일 읽기, 파일시스템 변경 감시, 커스텀 렌더러가 모두 API 자체에 없다. 구체적으로:

| 우리 핵심 기능 | OpenPets SDK v3 실태 | 판정 |
|---|---|---|
| `brew doctor` 등 셸 명령 실행 | API 자체가 존재하지 않음. `ctx.system`은 `info()`(platform/locale/timezone/theme/appVersion/online), `metrics()`(CPU/메모리/배터리), `openExternal()`, 클립보드가 전부 | ❌ 불가 |
| `.zshrc` 등 파일 읽기 | `ctx.files`는 `pick()`/`save()`뿐 — OS 파일 다이얼로그로 사용자가 매번 직접 고른 파일만 | ❌ 불가 |
| 설정 파일 변경 감시 | `docs/sdk.md`에 "no ambient filesystem watching" 명시 | ❌ 불가 |
| 3D 커스텀 렌더러 | `pet-format`은 스프라이트/애니메이션 애셋 기술 전용. "Pet packages should describe assets; they should not require arbitrary code execution" 명시 | ❌ 불가 |

3D 여부와 무관하게 진단 어댑터라는 핵심 기능이 플러그인 샌드박스 안에서 아예 돌지 않는다.

**참고**: OpenPets 저장소 자체는 건강하다(MIT, ★1,078, 2026-08-17 최신 커밋, 문서화 수준 매우 높음). 우리 용도에 맞지 않을 뿐이며, 발표에서 "실사 후 기각한 대안"으로 언급하면 기술 판단력의 근거가 된다.

**트레이드오프**: 기존 OSS 생태계에 올라타는 이점(배포·발견성)을 포기하고 처음부터 빌드해야 한다. `network:local` 권한으로 localhost HTTP 호출이 가능하므로 진단 엔진을 별도 로컬 데몬으로 띄우고 플러그인이 호출하는 우회로도 검토했으나, 사용자가 데몬과 펫 앱을 따로 설치해야 하는 마찰이 생기고 배포 타깃이 3개로 늘어 완주 리스크(G5)가 급등해 기각했다.

### ADR-003: Electron + TypeScript + React 채택 (Tauri/Rust 기각)
**결정**: 전 구간을 TypeScript로 통일하고 Electron + React를 쓴다.
**이유**: Tauri는 프론트를 React로 짜도 백엔드가 Rust라, 사람의 이해가 병목인 구조에서 리뷰 불가능한 코드 구간이 생긴다. 팀의 검증된 경험이 JavaScript/React다.
**트레이드오프**: Electron은 Tauri 대비 번들 크기·메모리 사용량이 크다. 이 프로젝트에서는 리뷰 가능성이 성능보다 우선한다.

### ADR-004: shellrc-doctor 로직을 의존성이 아닌 TypeScript 포팅으로 흡수
**결정**: `github.com/nord342/shellrc-doctor`(MIT, Python 단일 파일)를 런타임 의존성으로 호출하지 않고, 로직을 TypeScript로 포팅한다.
**실물 확인**: `github.com/nord342/shellrc-doctor` — Python 단일 파일 `shellrc_doctor.py`(약 20KB), MIT, ★0, 최근 커밋 2026-05-11(정체). `--json` 옵션이 이미 존재하며 `.zshrc:42` 형태로 파일:줄 번호를 제공한다. 원본 도구의 전체 기능 범위는 중복/죽은/미사용 alias, shadowed PATH, source 별 타이밍, 셸 시작 시간, nvm+asdf·pyenv+asdf 충돌이다 — 이 중 우리가 포팅하는 것은 중복 PATH·죽은 alias·존재하지 않는 source·중복 alias(`docs/specs/adapter-shell-rc-spec.md` FR-002~006)와 nvm+asdf·pyenv+asdf 충돌(같은 문서 FR-009)뿐이며, **shadowed PATH 자체 감지, source 별 타이밍 측정, 셸 시작 시간 측정은 포팅 범위에 포함하지 않는다**(v1 범위 밖).

**이유**: 의존성으로 호출하면 심사위원 머신에 Python이 없을 때(macOS 기본 미포함) 가장 중요한 어댑터가 통째로 침묵한다. 또한 핵심 차별점("파일:줄 지목")의 출력 형식을 남의 스키마 변경에 종속시키지 않기 위함이다. ★0에 3개월 정체된 저장소와의 결합 서사 가치도 낮다. **단일 파일 20KB라 포팅 자체가 현실적인 규모다.**
**트레이드오프**: 포팅 유지보수 비용을 직접 진다. 대신 `THIRD-PARTY-NOTICES.md`에 원저작자·저장소 URL·MIT 전문을 기재하고, 포팅한 소스 파일 상단과 README·보고서에 유래를 명시하는 고지 의무를 진다(`docs/SUBMISSION.md` "라이선스 체크리스트" 참조).

### ADR-005: 배포 타깃 2개 고정 (packages/core + apps/pet), CLI는 내부 전용
**결정**: 저장소는 `packages/core`(npm 라이브러리)와 `apps/pet`(Electron 앱) 2개 배포 타깃만 유지한다. `packages/core/src/cli.ts`는 내부 개발/테스트 진입점일 뿐 별도 제품으로 소개하지 않는다.
**이유**: "3개 이상의 배포 타깃"은 대회 채점 항목은 아니지만 1인·8일 완주에 불리한 리스크 요인(G5)으로 아카이브 원문에 명시되어 있다. 이전 초안은 이 규칙의 근거를 "루브릭 1-1: 배포 타깃 3개 이상 = 0점"으로 잘못 적었으나, 아카이브 원문(`archive/research/03-tech-trends-2026.md`) 확인 결과 이는 채점 항목이 아니라 "2주 안에 완주하기 불리한 특성" 목록의 한 줄이었다(오귀속 정정). 규칙 자체는 유지하되(1인·8일에 배포 타깃을 늘리면 완주가 위태롭다), **발표·보고서·README 어디에서도 "0점 규칙"으로 설명해서는 안 된다.**
**트레이드오프**: CLI를 독립 제품으로 키울 수 있는 확장 여지를 v1에서 포기한다.

### ADR-006: 스냅샷 저장 위치를 홈 디렉터리에 고정
**결정**: 스냅샷을 Electron의 `app.getPath('userData')` 대신 `~/.nosy/snapshots/latest.json`에 저장한다.
**이유**: 사용자가 직접 파일을 열어볼 수 있어야 신뢰가 생긴다는 것이 명시적 설계 판단이다.
**트레이드오프**: OS 표준 앱 데이터 디렉터리 관행에서 벗어난다. 대신 투명성을 얻는다.

### ADR-007: 스냅샷을 어댑터별로 분리 저장 + 실행 범위 한정 diff
**결정**: 스냅샷은 전체를 한 덩어리로 저장하지 않고 `{ adapter, ranAt, findings[] }` 레코드 단위로 분리 저장한다. 드리프트 비교는 이번 실행에 실제로 포함된 어댑터 범위 안에서만 수행하고, 포함되지 않은 어댑터의 레코드는 그대로 유지한다.
**이유**: 30분 주기 체크는 부하 관리를 위해 자체형 어댑터(shell-rc, version-manager)만 돈다. 전체 id 집합을 통째로 diff하면 그때마다 래핑형 Finding이 "사라짐"으로 오판되고 다음 전체 스캔에서 "새로 생김"으로 다시 오판된다 — 펫이 30분마다 헛되이 놀라는 앱이 된다.
**트레이드오프**: 스냅샷 구조와 diff 로직이 단순 전체 비교보다 복잡해진다. 이 두 규칙(어댑터별 분리 저장, 실행 범위 한정 diff)은 "선택이 아니다" — 둘 다 하드 제약이다.

### ADR-008: v1 fix 안전장치 5종을 하드 제약으로 둔다
**결정**: ① 실행 전 확인 ② 파일 수정은 `.bak.<타임스탬프>` 백업 후 ③ sudo 필요 명령은 자동 실행하지 않고 복사만 제공 ④ `fix.revert` 없는 항목은 되돌리기 버튼 비활성 + 실행 전 명시 ⑤ 파괴적 작업(삭제, 전역 설정 초기화)은 v1 fix 대상에서 아예 제외.
**이유**: 10월 기능테스트에서 심사위원이 자기 머신에서 직접 토글을 켜본다. 사용자가 무엇이 실행되는지 모른 채 시스템이 바뀌는 일이 있으면 안 된다.
**트레이드오프**: "펫이 알아서 다 고쳐준다"는 완전 자동화 서사를 포기하고, 사용자 확인 단계를 항상 거치는 쪽을 택한다.

### ADR-009: 로그인 시 자동 시작(LoginItem) 채택
**결정**: `apps/pet`를 macOS 로그인 항목에 등록한다(Electron `app.setLoginItemSettings({ openAtLogin: true })`). 사용자가 수동 실행하지 않아도 로그인 시 펫이 뜬다.
**이유**: 사용자가 참조 모델(상시 상주하는 데스크톱 펫)을 명시했다 — "진단이 필요할 때만 켜는 도구"가 아니라 "항상 떠 있는 동반자"로 자리잡아야 하며, 이는 드리프트를 놓치지 않고 즉시 감지한다는 핵심 가치와도 방향이 맞는다. Electron 내장 API 한 줄로 구현되므로 완주 리스크(G5)에 미치는 영향은 거의 없다.
**트레이드오프**: 사용자 동의 없는 부팅 시 자동 실행은 신뢰를 해칠 수 있다 — 최초 실행 온보딩에서 "로그인 시 자동 시작" 여부와 끄는 방법을 명시적으로 안내해야 한다. 세부 온보딩 UX는 `docs/UI_GUIDE.md` 비주얼 디자인 확정 시 함께 정한다.

### ADR-010: 확장 지점 라벨링만, 런타임 플러그인 로더는 v1 제외
**결정**: `DiagnosticHost` 주입과 `<PetView>` 렌더러 격리를 "확장 지점"으로 명시적으로 문서화한다(`docs/ARCHITECTURE.md` "확장 지점" 참조). 외부 코드·데이터를 런타임에 붙이는 실제 플러그인 로더·샌드박스는 만들지 않는다.
**이유**: OSS 발전 가능성(1-2, 6점)·커뮤니티 확장(2-4, 10점) 배점을 겨냥한 것인데, 전담 프로젝트인 `alterhq/openpets`(MIT, ★90)조차 "외부 플러그인 설치·샌드박스 실행은 계획됐지만 아직 안 나왔다"는 상태다. 우리보다 오래·좁게 이 문제만 파는 프로젝트도 못 만든 것을 8일 안에 만들려는 시도는 완주 리스크(G5)를 키운다. 반면 두 격리 패턴은 이미 존재하므로 라벨링만으로 같은 서사를 무료로 얻는다.
**트레이드오프**: 실제로 동작하는 플러그인 데모는 없다 — "확장 가능하게 설계됨"을 문서와 아키텍처로만 증명한다. 코드로 증명하는 것보다 설득력이 약할 수 있으나, 하드 게이트(G1·G2·G3) 근처를 지나가는 리스크를 피하는 쪽을 택한다.
**주의**: 외부 상태 push 채널(펫이 외부 프로세스로부터 알림을 받는 별도 채널) 같은 세 번째 확장 지점은 검토했으나 채택하지 않았다 — 진단 도메인 밖의 범용 알림 허브로 정체성이 흐려지고, `ADR-002`에서 기각한 openpets 경로를 스스로 재현하는 셈이 되기 때문이다. Claude Code·Codex 연결을 핵심 메커니즘으로 넣는 것도 여전히 재논의 금지(아래 "재논의 금지 항목" 참조) — 이 ADR은 그 경계를 바꾸지 않는다.

### ADR-011: Dock 아이콘 숨김 + 메뉴바 상주
**결정**: `app.dock.hide()`로 Dock 아이콘을 숨기고, 메뉴바(상태 표시줄)에 Tray를 상주시켜 앱 관리 진입점을 제공한다. 온스크린 펫은 그대로 주 UI이며, 메뉴바는 펫이 표현할 수 없는 조작(종료, 자동 시작 토글 등)만 담당한다.
**이유**: 세 가지가 겹친다. ① ADR-009로 로그인 시 자동 시작이 확정됐는데, 매 로그인마다 뜨는 상주 앱이 Dock을 한 칸 차지하면 ADR-009가 스스로 적어둔 트레이드오프("동의 없는 자동 실행은 신뢰를 해칠 수 있다")가 악화된다. ② ADR-009는 "자동 시작을 끄는 방법을 명시적으로 안내해야 한다"고 요구하는데 그 진입점이 어디에도 없었다. ③ 가장 결정적으로, 창이 `frame: false`이고 클릭 관통([[pet-window-spec]] FR-002)까지 적용되면 **사용자가 앱을 종료할 방법이 없다** — 10월 기능테스트에서 심사위원이 자기 머신에 설치해 실행하는데 끌 수 없는 앱은 그 자체로 감점 요인이다.
**트레이드오프**: "재논의 금지 항목"의 트레이 아이콘 항목과 표면적으로 충돌하는 것처럼 보인다. 그 항목이 금지한 것은 **펫을 대체하는** 트레이 단독 UI이며, 이 결정은 펫을 주 UI로 두고 메뉴바를 보조로 얹는 것이라 경계가 다르다 — 혼동을 막기 위해 아래 표의 문구를 "단독 방식"으로 조인다. 비용으로 메뉴바용 템플릿 아이콘 애셋(16×16 흑백)이 추가로 필요하고, `app.dock`은 macOS 전용이라 비-macOS 가드가 필요하다([[pet-window-spec]] FR-005).
